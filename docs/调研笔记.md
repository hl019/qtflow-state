# 调研笔记

本文件记录课题《面向自研平台的商务流程状态数据底座》的调研依据。所有判断均来自群内公开讨论与公司开源仓库的实证，不含个人推测。

## 一、痛点来源

关于状态不可见。赵子奕的原话是，邮箱自动化的主要难点在于需要读海量的上下文，都不一定能猜得出它的实际状态，最大的难点就是理解这个工作的状态是什么样的，光凭邮箱的信息有时候会不够，规则稍微一乱一下就没法读了。

关于失控规律。张果在群内描述，项目前期一般看起来正常，一到中后期就开始出问题，特别是后期；几个项目堆在一起时，整个团队的协同就立刻卡顿。现有应对方式是要求商务经理查验收清单，但这一习惯尚未建立起来。

关于验收标准。张果在讨论中指出，验收这一块实际上主要就是数据质量，目前合同也比较模糊，公司也在想办法把这块标准明确一下。

## 二、仓库实证

qtcloud-business 的 README 中明确写着，CLI 当前版本只做无状态计算，不保存报价单，也不读取服务端数据。这是"状态不可见"最直接的技术证据——痛点是公司自己写在文档里的，不是外部观察者的推测。

qtcloud-business 已经建立了报价、合同、履约三个数据模型，前端也有状态徽章组件，缺的是持续沉淀的状态数据。

qtcloud-business 在 8 月 23 日的提交是"章程执行率汇总与操作人署名留痕"，表明状态可观测性正是当前正在补齐的方向。

qtdata 采用 Python FastAPI 服务端加 pytest 测试体系，最近一次提交是"dataset API 参考实现（自 qtadmin provider 迁移）"，说明数据正在跨系统迁移，统一数据层是刚需。

handbook 的 qtdata/connect/email.md 提供了 E1 至 E18 的完整工作流定义，每个节点包含触发、发件角色、邮件标题、期望响应与时限五个字段，可直接作为状态机 Schema 的来源。

## 三、前提认知

邮件工作流本身是过渡方案。张果已明确说明，各个业务都在自研自己的系统并配套后台系统，邮件流程承载的业务将迁移至平台，换成平台后大量通知步骤会被简化。

赵子奕提出，收益更高的方法其实应该是自研平台，然后把自动化流程跟自研平台的流程对接起来。这里的关键字是"对接"——数据层需要独立于上层载体存在，既能服务当前的邮件流程，也能服务未来的平台接口。

因此本课题不试图优化邮件流程本身，也不做邮件自动发送，而是为过渡期与平台期提供统一的状态数据层。

## 四、需求优先级

张果多次强调公司想要的是质量检查和控制工具，而不是自动化工具，原因是自动化容易找到替代，质量控制非常稀缺。这一点直接决定了本课题的定位：产出的是可审计、可校验的数据底座，而不是替代人工的自动化流程。

张果同样明确反对用 AI 生成一大堆看起来正确的清单，要求产出经过人类仔细裁剪与思考。赵子奕则提供了 AI 使用的正面方法：让 AI 从一大堆混乱的原始信息中梳理一个主线故事，讲一遍之后再从里面提炼需求。

## 五、执行云 v0.1（9 月 3 日发布）

9 月 3 日，量潮执行云 v0.1 发布，官方定位是「让执行从靠人记得，变成靠系统看清」的任务系统。与本课题高度相关，值得单独记录。

官方描述的三层问题：任务的生命周期没有被承载，消息发出、大家收到、开始执行，然后过程就消失了；优先级在传话里失真，信息每多中转一层就失真一分；老板在替系统干活，他必须亲自问才能知道进度。一句话总结是「事情的执行，缺一个统一、透明、可读写的事实源」——这与本课题的问题陈述几乎完全一致，可作为痛点的最新佐证。

v0.1 的当前局限同样关键。官方明确写明，当前是「个人任务」模型，**没有负责人、没有复核人、没有下一步动作、没有卡点、没有截止**；信息维护靠命令行加周报纪律撑着。团队对任务的真正定义是「团队内交付结果的单元」——做完要给另一个人验收，任务和结果要在两个人之间流转。四字段承载不了这件事。

下一步计划是补上 Owner、Next Action、Blocker，加红黄绿与节点报警（到点不点亮自动报警，不靠自觉）。

**对本课题的意义**：执行云缺的 Owner、Next Action、Blocker、截止，正是状态数据层可以供给的东西。本课题的数据层独立于上层载体，执行云可作为其首个对接场景。这也让「自研平台」这个前提有了具体的产品对象，而不再是抽象表述。

## 六、数据可获取范围的澄清（9 月 4 日）

向赵子奕申请真实脱敏样本后得到回复：完整项目周期的数据包含前期沟通内容，脱敏难度大；建议参考 `quanttide-gallery-of-project-management` 的 `stage/retrospective.md`。

研读该文档后，可获取范围得以明确。该文档是「项目交付期复盘」模板，以某面板数据分阶段交付项目为例，结构为项目概况、关键节点表、复盘发现、改进方向四部分。关键节点表覆盖前期交付、后期需求、方案澄清、多轮口径修正、报价与交付、收尾六个阶段。**不含前期商务沟通与报价阶段的原始对话**。角色仅记录「商务经理 1 人、软件工程师 1 人、外部客户」，原始邮件与群聊未保留。

由此得出两点结论。第一，可获取的真实样本是**脱敏后的项目复盘文档**，而非原始邮件或群聊。第二，测试集覆盖范围限于**交付期节点**（E 阶段后期至收尾），前期对话（E1 至 E6 段）大概率无法覆盖。验收指标需据此校准，不能按完整周期表述。

该复盘文档同时提供了痛点的独立佐证。其「复盘发现」一节记载：后期详细技术验收口径靠邮件附件、算例和即时通讯补充说明逐项拼合，没有一开始就固化为完整验收文档；缺失完整签署版合同文本，合同条款复盘无法完整进行。这正是「状态散落、无法追溯」的实证，且由公司自己在复盘中写出。

## 七、考核规则变化（9 月 4 日）

两项议事对课题交付方式产生直接影响。

**课题结项初审改为两阶段**：先向实训基地代表大会提交，**侧重于「能不能让同事们用起来」**，再提交公司终审。基本规则参考课题立项，参与审议的范围扩大到最大。

这意味着交付物的评价标准是**实用性**，而非技术先进性。交付重点应从「技术多强」切到「同事能不能用」：能否一键跑起来、输出能否看懂、遇到问题能否自查、能否直接拿到结论。

**毕业要求从工时制改为代金券贡献制**：原为积分加工时（1 个月实训加 3 个月实习），改为以代金券积累量为标准。实训与实习证明的初审权下放给实训基地，包含规则制定与初审两个环节。
