# 字段口径说明

本文档说明解析器输出的每个字段「是什么、从哪来、怎么判、抽不到怎么办」。

设计前提：解析器只抽取事实，不判断对错。状态是否异常由人判定，系统只负责把事实与证据摆到人面前。

---

## 输出字段总览

| 字段                  | 含义            | 抽取来源                | 抽不到时   |
| ------------------- | ------------- | ------------------- | ------ |
| `project`           | 项目名称          | 邮件标题的方括号内           | `null` |
| `node`              | 流程节点（E1–E18）  | 标题后半段优先，正文兜底        | `null` |
| `subject`           | 邮件标题原文        | 标题行                 | `null` |
| `actor`             | 发件/责任角色       | 正文角色关键词             | `null` |
| `date`              | 邮件日期          | 正文日期，归一化 YYYY-MM-DD | `null` |
| `expected_response` | 期望对方做什么       | 正文首个「请」字句           | `null` |
| `evidence`          | 证据原文（前 120 字） | 邮件正文开头              | 始终有值   |
| `source`            | 来源文件名         | 输入文件                | 始终有值   |
| `parsed_at`         | 解析时间          | 系统时间                | 始终有值   |

---

## 逐字段口径

### `project` —— 项目名称

- **从哪来**：邮件标题中方括号 `[]` 或 `【】` 内的内容。
- **怎么判**：匹配 `[项目名称] - 节点描述` 格式，取方括号内文本。
- **示例**：标题 `[某某高校科研数据项目] - 合作承接确认与信息收集` → `某某高校科研数据项目`
- **抽不到时**：`null`。标题无方括号时不影响其他字段抽取。

### `node` —— 流程节点

- **从哪来**：先查标题后半段，再查正文。节点关键词见下表。
- **怎么判**：按固定顺序匹配，**E3b 优先于 E3**（避免把降价协商误判为常规报价）。标题匹配不到时回退到正文匹配。
- **节点关键词**（来源 `quanttide-handbook-of-business-entity/qtdata/connect/email.md`）：

| 节点  | 关键词     | 节点  | 关键词      |
| --- | ------- | --- | -------- |
| E1  | 承接确认    | E10 | 需求变更     |
| E2  | 项目策划书   | E11 | 验收通知     |
| E3  | 商务报价单   | E12 | 项目交付物    |
| E3b | 关于报价的沟通 | E13 | 尾款支付通知   |
| E4  | 报价确认    | E14 | 开票资料     |
| E5  | 商务合同    | E15 | 发票已开具    |
| E6  | 合同已盖章   | E16 | 项目结项确认   |
| E7  | 项目正式启动  | E17 | 交付后支持与回访 |
| E8  | 进度周报    | E18 | 长期合作邀请   |
| E9  | 项目风险同步  |     |          |

- **抽不到时**：`null`。

### `subject` —— 邮件标题原文

- **从哪来**：识别 `主题:` / `标题:` / `Subject:` 三种写法；都没有时取第一行非空文本。
- **用途**：保留原始标题，便于人工核对解析是否正确。

### `actor` —— 责任角色

- **从哪来**：正文中出现的角色关键词。
- **怎么判**：按 `商务经理 / 项目经理 / PM / 财务 / 销售` 顺序匹配，**首次命中即返回**。`项目经理` 归一为 `PM`。
- **已知局限**：只识别正文中**明确写出**的角色。若邮件未署名或只写人名，会返回 `null`——这是刻意设计，不猜测。
- **抽不到时**：`null`。

### `date` —— 日期

- **从哪来**：正文中的日期，支持 `2026年8月15日` 与 `2026-08-15` / `2026/08/15` 两种写法。
- **怎么判**：**取正文中第一个匹配到的日期**，归一化为 `YYYY-MM-DD`。
- **已知局限**：若正文出现多个日期（如「原定 8 月 10 日，现延至 8 月 20 日」），只取第一个，可能不是最终日期。这种情况需人工看 `evidence` 确认。
- **抽不到时**：`null`。

### `expected_response` —— 期望响应

- **从哪来**：正文中第一个以「请」开头的句子，保留完整表述到句末标点。
- **用途**：回答「这封邮件在等对方做什么」——是状态判断的关键输入。
- **抽不到时**：`null`。邮件若只是通知、不需要对方回复，则为 `null`，属正常情况。

### `evidence` —— 证据原文

- **从哪来**：邮件正文前 120 字，换行替换为空格。
- **用途**：**每条记录都能追溯到原文**，供人工复核。这是本工具的核心——不要求使用者盲信系统判断。
- **始终有值**（除非输入为空文本）。

### `source` / `parsed_at`

- `source`：来源文件名，用于追溯这封邮件来自哪个输入文件。
- `parsed_at`：解析时间（ISO 8601），用于判断数据新鲜度。

---

## 三条设计原则

**一、每条记录都保留证据。** 所有抽取结果都附带 `evidence` 原文，供人工复核，不要求使用者盲信系统的判断。

**二、抽取失败返回空值。** 字段无法确定时返回 `null`，**不做猜测，不填充默认值**。宁可留空，不可编造。

**三、只抽取事实，不判断对错。** 「这封邮件是否超时」「这个项目是否异常」由人判定，系统只负责把事实摆到面前。

```json
  "parsed_at": "2026-09-01T16:38:00"

```

## 已知局限（诚实说明）

当前版本为**规则解析（正则）**，不依赖外部服务，保证可离线运行。已知局限：

1. **只识别明确写出的角色**，未署名邮件返回 `null`。
2. **多日期场景只取第一个**，可能不是最终日期。
3. **表述多样的邮件覆盖有限**——后续会接入 LLM 处理，规则解析作为兜底与校验基准。
4. **当前仅覆盖 E1 示例节点**，其余节点待真实样本接入后验证。

这些局限不影响工具的核心价值：它给出的每条记录都带证据，人可以随时复核、随时修正。
