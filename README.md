# qtflow-state

面向自研平台的商务流程状态数据底座。

把量潮 E1 至 E18 邮件工作流里的状态变成结构化数据，让流程状态在过渡期（邮件）与平台期（qtcloud-business / qtdata）都看得见、能回溯、能校验。

## 依据

节点定义取自[《订单邮件工作流》](https://github.com/quanttide/quanttide-handbook-of-business-entity/blob/main/qtdata/connect/email.md)，共 18 个邮件节点（E1–E18，另有降价协商分支 E3b），分属 7 个阶段：订单承接、方案报价、合同启动、执行监控、验收交付、尾款发票、收尾留存。这份工作流的原则是一句话：「每一步关键节点均以邮件书面确认」。

工作流不是凭空定的，它要落实的是章程里已经写明的要求，从公司层到业务线层再到审计：

- **《量潮科技项目管理总纲》**（公司层，[`project/index.md`](https://github.com/quanttide/quanttide-bylaw-of-business-entity/blob/main/project/index.md)）把项目切成五个阶段，第六条「阶段流转条件」逐条写明怎么才算过关，其中三句是：「（二）谈判阶段→执行阶段：客户确认报价，首付款到账（如适用）。」「（三）执行阶段→交付阶段：交付物经内部质量审核通过。」「（四）交付阶段→复盘阶段：客户验收确认完成，交付物移交完毕。」
- **《量潮科技项目管理章程》**（数据业务线细则，[`qtdata/project.md`](https://github.com/quanttide/quanttide-bylaw-of-business-entity/blob/main/qtdata/project.md)）把阶段细化为六个，并给出与本课题最直接的那句话：「项目分为六个阶段，各阶段必须有明确的**权责流转标志**方可进入下一阶段。」标志本身也写死了四个——客户签署确认的需求文档或伪代码流程、生效的《商务合同》且首付款到账、客户签署的《最终验收报告》、正式交付邮件发出且反馈期结束。
- **《量潮数据审计章程》**（[`qtdata/audit.md`](https://github.com/quanttide/quanttide-bylaw-of-business-entity/blob/main/qtdata/audit.md)）规定审计要查的正是这件事，第十二条：「审查项目是否按生命周期阶段流转，各阶段权责流转标志是否完整。」

链条在这里闭合：**章程规定必须有标志，审计章程要求查标志完不完整，邮件工作流规定用邮件确认，本课题让这个「查」能跑出来。**

**阶段数三处不同（总纲 5、业务线章程 6、邮件工作流 7），不是打架。** 《项目管理总纲》第三条写明「各业务线可在本章程框架内制定本业务线的项目管理细则」，邮件工作流是把商务段拆得更细以对上具体的邮件动作。`docs/workflow-schema.yaml` 里用的是最后一层（7 个阶段），与业务线章程六阶段的对应关系大致是：

| 业务线章程（6 阶段） | 邮件工作流（7 阶段） | 节点 |
|---|---|---|
| 需求 | 订单承接 | E1 |
| 报价与合同 | 方案报价、合同启动 | E2–E6 |
| 启动 | （工作流里是独立一封，schema 归入合同启动段） | E7 |
| 执行 | 执行监控 | E8–E10 |
| 验收 | 验收交付 | E11–E12 |
| 收尾 | 尾款发票、收尾留存 | E13–E18 |

映射是按各阶段定义逐条对出来的，不是章程原文规定——章程管「要有什么标志」，工作流管「标志长在哪封邮件里」。

**两处边界要说清楚。** 业务线章程的六个阶段里，只有四个写明了「权责流转标志」（需求、报价与合同、验收、收尾）。「启动阶段」写的是核心产出（启动会纪要、任务分配、沟通渠道建立），「执行阶段」写的是输出（定期进度报告、阶段性交付物）。这两段的认定方式不同：

- **启动阶段的动作不发生在邮件里**（开会、分任务、建群），所以那一段本课题不覆盖。E7「项目正式启动」名字虽然像，但它对应的是章程「报价与合同阶段」的标志——首付款到账之后发出的确认邮件，schema 里归在合同启动段，正常参与缺失判定。
- **执行阶段的产出本身就是邮件**（进度报告、阶段性交付物），审计附录一也把「是否有进度汇报及排期确认」列为检查项，所以 E8–E10 纳入判定。

覆盖范围跟着章程写的东西走：章程写明要求的，工具判有无；章程没写、也不在邮件里的，工具不替它立规。

## 为什么做这个

题目来自实训基地 9 月立项，材料是一次真实项目的结项复盘（脱敏后使用）。做这个不是因为缺一个工具，是因为复盘时发现：一个完整走完的项目，邮件里留痕的缺口比预想的大。缺的具体是什么，见下一节。

量潮的商务流程长期横跨邮件、表单、表格与群聊，状态散在各处，衔接靠人搬。结果是项目到中后期经常说不清「现在卡在哪、还差什么」——验收结论没有、合同文本找不到、复盘写完就结束。这些都是记录层面的缺口，不是能力问题。

## 能拿来干什么

[《量潮数据审计章程》](https://github.com/quanttide/quanttide-bylaw-of-business-entity/blob/main/qtdata/audit.md)第五条规定公司实行季度常规审计与结项审计相结合的制度，第十五条要求审计人员依照第三章标准逐项检查、填写附录一的《项目审计检查清单》。附录一「项目管理」下的九项是：是否有策划书及客户确认、是否有报价单及定价确认、需求/方案变更是否有审批、是否有进度汇报及排期确认、是否有交付邮件及客户验收、是否有项目复盘及资产归档、是否定期向客户汇报进度、人员变动是否及时同步、关键卡点是否上报管理层。

这九项目前靠人翻邮件核，一个项目核一次，每季度再审一次。本课题把它变成一条命令：`--missing` 列出哪个阶段该有的记录没有，`--trace` 拉出某个项目的完整往来。九项里有八项能对上具体节点——策划书→E2，报价单与定价确认→E3/E4，变更审批→E10，进度汇报与排期确认→E8，交付邮件与客户验收→E11/E12，复盘与归档→E16，定期汇报→E8，关键卡点→E9。剩下「人员变动是否及时同步」没有对应的邮件节点，仍需人工确认。

不用讲抽象的「降本」，看一次真实结果就够了。把上面那份脱敏复盘对回章程，三个权责流转标志的状态是：

| 章程要求的标志 | 那份项目的记录情况 | 工具把它归到 |
|---|---|---|
| 生效的《商务合同》，且首付款到账 | 没有完整签署版合同文本，付款节点无法核对 | 🔴 应有但缺失（E5、E6） |
| 定期进度汇报 | 全文未提及进度周报 | 🔴 应有但缺失（E8） |
| 客户签署的《最终验收报告》 | 现有记录中没有更晚的最终验收结论 | 🟡 待确认（E16） |

跑出来的报告长这样：

```
🔴 应有但缺失（流程已走到其后，但无任何记录）—— 3 个
   E5  商务合同
   E6  合同已盖章
   E8  进度周报
🟡 待确认（项目已进入收尾期，未见记录，需人工确认是否线下发生）—— 4 个
   E15  发票已开具
   E16  项目结项确认
   E17  交付后支持与回访
   E18  长期合作邀请
```

最后一行为什么落在「待确认」而不是「缺失」：项目最后一条记录停在 E13，验收与结项还没到，工具不替人下结论，只标出来让人去核。这也是设计原则第三条。

这三个缺口不是工具找出来的新问题，是复盘时人自己写下的原话。本课题做的事，是把这件事从「事后复盘时才想起来问」变成「跑一次就知道」——审计附录一里「项目管理」那九项，大部分可以直接对照这份报告判定。

## 定位

这一层不绑在邮件上。邮件只是过渡期的载体——现在商务流程走邮件，等上了 qtcloud-business / qtdata，同一套状态定义可以直接沿用，也能为课堂工作台（class.quanttide.com）、执行云（qtcloud-execute）提供执行状态数据。所以现在做的不是「给邮件做张表」，是把「一个项目走到哪一步」这件事先定义清楚。定义清楚了，换什么载体都不用重来。

## 30 秒上手

**环境要求**：Python 3.10 或更高版本。代码只用标准库，不需要 pip 安装任何依赖，也不必新建虚拟环境。

在这个前提下，三条命令跑通全链路。

> 下面**前三条只用仓库自带的示例邮件，开箱可跑**。其余命令里的 `--retro` / `--gt` / `parsed_retrospective.json` 需要另外提供材料（原因见「当前进度 → 关于样本量」），**代码路径本身不依赖这些文件**。

```
python project/parser.py
python scripts/verify_delivery.py
cat project/data/parsed_states.json
```

（Windows 的 CMD 里 `cat` 换成 `type`；PowerShell 里可以直接用 `cat`。）

**解析项目复盘报告**（一份报告含完整时间线，会产出多条状态记录）：

```
python project/parser.py --retro 你的复盘报告.md
cat project/data/parsed_retrospective.json
```

**评估抽取准确率**（对照人工标注基准，输出准确率 + 覆盖率 + 逐条对照）：

```
python project/evaluate.py --pred project/data/parsed_retrospective.json --gt 你的标注基准.md
```

标注基准是一个 Markdown 表格，列为 `# | 日期 | 事件 | E 节点 | 置信度 | 角色 | 证据原文（摘要）`，脚本按日期分组比对，低置信项默认不计入严格口径。

**落库与查询**（SQLite，表围绕 项目 / 节点 / 状态 / 证据 四概念）：

```
python project/state_db.py --load project/data/parsed_retrospective.json
python project/state_db.py --status      # 各项目当前处于哪个节点
python project/state_db.py --trace 关键词  # 某项目全链路（带证据）
python project/state_db.py --missing     # 哪些节点没有任何记录
python project/state_db.py --stats       # 统计（含 S2 可溯源比例）
```

**交付清单校验**（把「没记录」分成三类，输出人能看懂的校验报告）：

```
python project/validator.py --pred project/data/parsed_retrospective.json --check
python project/validator.py --pred project/data/parsed_retrospective.json --gt 你的标注基准.md --evaluate
```

三分类规则：**应有但缺失**（流程已走到其后，该节点却无记录）、**流程未走到**（项目仍在推进，尚未到达）、**待确认**（项目进入收尾期后仍未见记录的环节，需人工确认是否线下发生）。收尾判定阈值默认「距最后记录 >30 天」，可用 `--as-of` / `--gap-days` 调整。`--evaluate` 对照人工标注基准输出 S3 校验一致率与逐节点对照。

「应有但缺失」严格说是「按标准流程应有」——《项目管理总纲》第六条末句写了「未经审批不得跳阶段流转，但规模较小的项目可按简化流程执行」。是否豁免由项目负责人判断，工具只负责把缺的摆出来，这也是设计原则第三条（不判断对错）的由来。

报告中的时间线写作 `2026-02-05：事件描述` 或 `2026-06-16 至 2026-06-18：事件描述`（范围取起始日期）即可被识别，每行输出一条带证据原文的状态记录。

Windows 用户更简单：直接双击 `run-demo.bat`，自动完成解析与自检。

**看到这个输出就说明装好了**：

```
qtflow-state 交付自检
--------------------------------------------------
  [PASS] 示例邮件存在 —— 共 1 个文件
  [PASS] 解析器可导入
  [PASS] E1.txt 关键字段抽取 —— 项目=某某高校科研数据项目 节点=E1
  [PASS] 证据字段完整 —— 每条记录均保留 evidence
  [PASS] JSON 输出可回读 —— 1 条记录
--------------------------------------------------
结果：5/5 项通过
交付自检通过
```

只要出现 `结果：5/5 项通过` 和 `交付自检通过`，环境就是好的。任何一项 `FAIL` 都会直接告诉你哪一步出问题。

## 当前进度

解析 → 落库 → 查询 → 校验，四条链路已经打通，**四项验收指标均有可复现实测值**。

| 验收项          | 目标    | 实测（对照人工标注基准）                       |
| ------------ | ----- | ------------------------------------ |
| S1 状态字段抽取准确率 | ≥ 90% | **100%**（准确率 17/17；覆盖率 17/18，两个口径见下）              |
| S2 状态记录可溯源   | 100%  | **18/18**，每条均带 `evidence`            |
| S3 交付清单校验一致率 | ≥ 95% | **100%**（15/15，逐节点对照可复现）             |
| S4 全链路可独立运行  | 可独立运行 | JSON 落进本地 SQLite，查询与校验不连邮件服务器、不依赖任何外部服务 |

**S1 两个口径都给（不挑好看的那个）**：准确率（抽出来的有多少是对的）**17/17 = 100%**，覆盖率（人工标注的节点有多少被抽到）**17/18 = 94.4%**。少的 1 条是标注基准第 20 条「E16 最终验收结论（缺失）」——它记的是一个**本该有却没有的节点**，原文里没有对应文本可抽，属于校验器应当报告的缺失，不是抽取失败。另外解析器在 2026-07-01 抽出的 E1，人工也标了 E1 但置信度为「低」，按严格口径不计入分母——这条其实抽对了。

**关于样本量（如实说明）**：当前测试集为 **1 个完整项目**（20 条人工标注，严格口径 18 条），立项验收要求为不少于 2 个完整项目，第 2 个项目已向公司申请待接入。上述数值按现有样本计算，评估脚本可复现——换一份材料重跑即可，无需改代码。

> ⚠️ S3 的「待确认 / 流程未走到」分类依赖**校验基准日**（默认当天）与 **30 天阈值**：同一份数据换一个基准日跑，结果会变。README 里的 15/15 是在基准日距最后一条记录超过 30 天时得到的。

> 标注基准与原始样本**含客户信息，不随仓库发布**（见 `.gitignore` 的 `test-samples/`）。因此仓库内直接跑 `--gt` 需要另行提供基准文件；解析与校验的**代码路径可独立复现**，`run-demo.bat` 走的是仓库内自带的示例邮件。

**两次真实的规则修复**（评估的意义在于暴露问题，而不是输出好看的数字）：

1. 首跑 S1 为 87.5%（未达标）：「客户因报销要求重开四张英文发票」被判为 E15 发票已开具（人工标注 E14 开票资料）。根因是 E15 规则含「重开/补开」且排在 E14 前——但重开/补开是**客户的开票要求**，票尚未开出。修正为 E15 只认完成态表述后，S1 升至 100%。
2. S3 首评 93.3%（未达标）：人工标注 #16 为「修订报价明细；客户接受价格」= E3 + E4 双节点，解析器每行只取首个命中导致 E3 漏抽，校验器随即把 E3 误报为缺失。增加白名单配对（主命中 E4 时若行内含 E3 提示词则补一条记录）后，S3 升至 100%。

第二份样本到位后，同一套脚本直接重跑全部评估，`parser.py` / `evaluate.py` / `validator.py` 都不需要改。

## 输出示例

解析结果写入 `project/data/parsed_states.json`，单条记录形如：

```json
{
  "project": "某某高校科研数据项目",
  "node": "E1",
  "subject": "[某某高校科研数据项目] - 合作承接确认与信息收集",
  "actor": null,
  "date": "2026-08-15",
  "expected_response": "请您提供以下信息（如有资料可直接回复附件）：",
  "evidence": "主题：[某某高校科研数据项目] - 合作承接确认与信息收集  X老师您好，...",
  "source": "E1.txt",
  "parsed_at": "2026-10-17T15:06:41"
}
```

上面这条就是 `python project/parser.py` 的真实输出。两处需要说明：`actor` 为 `null`，因为示例邮件落款写的是「商务负责人」、与 Schema 里的角色名「商务经理」不同名，按设计原则第二条留空而不猜；`parsed_at` 是运行时刻，每次跑都不同。

每个字段的含义、抽取规则、抽不到时怎么办，见 [字段口径说明](docs/字段口径说明.md)。

## 设计原则

三条原则都是为了让结果能被人复核，而不是让人相信系统。

第一，每条记录都保留证据。所有抽取结果都附带 evidence 原文，供人工复核，不要求使用者盲信系统的判断。

第二，抽取失败返回空值。字段无法确定时返回 null，不做猜测，不填充默认值。宁可留空，不可编造。

第三，只抽取事实，不判断对错。状态是否异常由人判定，系统只负责把事实摆到面前。

这三条指向同一件事：本仓库交付的是检查工具，不是决策工具。[《量潮科技项目质量章程》](https://github.com/quanttide/quanttide-bylaw-of-business-entity/blob/main/project/quality.md)第十七条「管理质量」第一项就是过程审计——「确保项目活动遵循既定流程与标准」。本课题做的正是这件事在邮件上的自动化：不判断项目做得好不好，只报告流程该有的痕迹有没有留下。

节点定义在 `docs/workflow-schema.yaml`：18 个节点（含降价协商分支 E3b）、7 个阶段、每个节点的触发与期望响应。解析时用的关键词与优先级写在 `parser.py` 顶部的 `NODE_KEYWORDS` 与 `RETRO_NODE_HINTS`，每条注明了出处和排序理由——`RETRO_NODE_HINTS` 的顺序就是优先级，更具体的表述排在前面，避免被宽泛词提前命中。节点有增减时，yaml 与这两处需要同步改。
