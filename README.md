# chat-kb · 群聊高价值信息抽取（最小可用版）

## 为什么做这个

新人进群有两个卡点，是群里同学自己提出来的：

1. **不敢问**——担心问题太基础，卡久了就慢慢不参与了
2. **翻不到**——群里其实沉淀了大量高价值信息（课题灵感、公司真实但还没解决的问题、流程解释、常见答疑），但散落在上千条聊天记录里，新人根本找不到

这个工具做一件事：把飞书群导出的原始消息，抽成**三类可检索的结构化条目**，让新人一条命令就能查到"群里以前是怎么说的"。

它是 `qtflow-state` 解析器能力的横向迁移——同一套内核（从非结构化文本里抽结构化记录），从"商务流程状态"迁到"群聊知识沉淀"上。

## 30 秒上手

```bash
# 1) 抽取：从群消息 JSON 抽成知识库
python kb_extract.py --input data/raw_messages.json --out data/kb.json

# 2) 看结果：分类统计 + 每类示例
python kb_extract.py --kb data/kb.json --stats

# 3) 检索：查"群里以前怎么说的"
python kb_extract.py --kb data/kb.json --query 验收
```

预期输出（1）：

```
读入消息 1103 条（已过滤系统消息与碎片）
共抽取高价值条目：210 条
  课题灵感     58 条  (27.6%)
  流程解释    143 条  (68.1%)
  答疑         9 条  ( 4.3%)
```

预期输出（3）：

```
检索「验收」：命中 12 条
  [流程解释] 2026-08-30 成员B
    我们现在的做法是会要求商务经理去查验收清单，但是这个习惯还没建立起来…
```

## 三类口径（字段说明）

| 类型             | 含义                   | 判定信号（节选）                         |
| -------------- | -------------------- | -------------------------------- |
| `idea` 课题灵感    | 公司真实需求、可做方向、还没人解决的问题 | 灵感 / 课题 / 众包需求 / 没动工 / 痛点 / 更感兴趣 |
| `process` 流程解释 | 怎么做 XX、规则是什么、入口链接在哪  | 流程 / 步骤 / 入口 / 规则 / 验收 / 提交 / 申请 |
| `qa` 答疑        | 提问 + 回答配对（带上下文）      | 短提问（<80字）+ 10 分钟内他人回复 + 用词相关     |

判定是**打分制**，不是关键词命中就归类：强信号 +3、弱信号 +1，总分 <3 判为日常闲聊丢弃。

## 两个已修的误判（说明规则为什么这么写）

1. **长篇观点被误判成流程说明**——长文里"怎么""需要"会反复出现，导致弱信号刷分。修法：文本越长，弱信号越早封顶（`>120字` 封顶 2 分）。
2. **修辞设问被当成真提问**——"为什么要把 A 和 B 合并呢？"是自问自答，不是提问。修法：只认 <80 字的短提问，且回复需与提问有用词重叠（避免"接话"被当成"回答"）。

修完答疑从 27 条降到 9 条，剩下的都是真问答。

## 已知边界（不吹，先讲清楚）

- **规则是启发式的，不是 LLM**：覆盖率和准确率还有空间，长文归类仍会摇摆（如一篇机制分析的長文可能落在"流程解释"）
- **答疑依赖上下文**：目前只在后续 8 条、10 分钟窗口内找回复，跨时段解答会漏
- **没做增量**：每次全量重跑，消息多了再考虑增量更新

## 脱敏（对外分享前必须开）

群聊内容含真实姓名与内部信息。写入公开仓库或对外演示时：

```bash
python kb_extract.py --input data/raw_messages.json --out data/kb_anon.json --anonymize
```

脱敏会把**群内出现过的所有名字**（不只是发言人，还包括正文里被 @、被提到的）统一替换为 `成员A/B/C`。

> 纪律：原始导出数据 `raw_messages.json` 与未脱敏的 `kb.json` **不进公开仓库**。
